# トラブルシューティングのナレッジ化

このセッションで解決した（または切り分けが進んだ）問題を、後で同じ症状に当たったときに最短で解決できる形のノートにして保存する。

## 保存先

`<出力先を設定する>`

- ファイル名: `YYYY-MM-DD <短い日本語タイトル>.md`（日付は `date +%F` で取得）
- 保存前に同じトピックの既存ノートがないか Glob で確認し、あれば新規作成せず追記・更新する

## 書き方のルール

- このセッションで実際に確認した事実だけを書く。推測のまま終わった箇所は「推定」と明記する
- 決め手になったコマンドは実際に実行したものをそのまま載せる（出力は要点だけ）
- 調査中にミスリードだった仮説も「紛らわしかった点」として短く残す（次回同じ回り道をしないため）
- 端的に書く。bold の多用や硬い言い回しはしない
- 「会話で〜した」のようなセッションのメタ文脈は書かない。事実と手順だけを書く

## ノートの構成

```markdown
---
date: YYYY-MM-DD
tags: [troubleshooting, <関連タグ2〜4個>]
---

# <症状が一目でわかるタイトル>

## 症状

何をしたら何が起きたか。エラーメッセージは原文のまま。

## 環境

OS / ツールのバージョン / 対象プロジェクトなど、再現に関係する範囲だけ。

## 原因

確定した根本原因を 1〜3 文で。

## 切り分けの流れ

実際に辿った順で番号付きリスト。各ステップに「確認したこと → わかったこと」を書く。
ミスリードだった仮説もここに含める。

## 解決方法

再発時にそのまま実行できる手順・コマンド。

## 学び

次回の切り分けを速くする一般則があれば 2〜4 個。なければ節ごと省略。
```

## 手順

1. `date +%F` で今日の日付を取得する
2. セッションを振り返り、症状・環境・切り分けの流れ・原因・解決方法を整理する
3. 保存先を Glob して同トピックの既存ノートを確認する
4. ノートを書き、保存したパスをユーザーに報告する
